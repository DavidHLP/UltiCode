## 1. 执行摘要

这份计划覆盖范围广（22 个 commit、10 大 Phase、5 周排期），对核心 bug（虚拟 AC 污染真实榜、`findByContestIdAndUserId` 不区分身份）的诊断正确，但**在实施层面存在 8 个 CRITICAL/HIGH 级系统性缺陷**：(1) Migration 与 schema 现状存在多处致命冲突（HMAC 64 字符 vs `varchar(40)`、现有 unique key 与新 unique key 语义冲突、slug rename 缺 301 重定向），合上去生产 100% 引发线上故障；(2) 22 个原子 commit 的中间态在生产不可编译/不可单独回滚，违反"小步可 revert"自身原则；(3) **零 feature flag 闸门**，5 周全量铺开没有 SRE kill switch；(4) WS、scoring、rating 三大模块均无双写/shadow-mode，回滚成本是手工 SQL 修复；(5) 完全缺失可观测性、压测基线、staging 策略、on-call 文档。

## 2. 已确认的 CRITICAL Finding

> v1/v2 两名审查者结论一致：`CONFIRMED`。

### CRIT-1 · DB-1 — `is_virtual IS NULL` 反向填充针对零行，迁移是假修复
- **位置**：`docs/CONTEST_AND_VIRTUAL_CONTEST_FIX_PLAN.md` §1.2 "前置要求: 把历史 is_virtual IS NULL 统一修成 false"
- **证据**：`init-db/migrations/V20260602_120000__Create_All_Tables.sql:151,223,303` 三处 `is_virtual tinyint(1) NOT NULL DEFAULT '0'`，物理上不可能存 NULL
- **结论**：UPDATE 是空操作，operator 看到"清理成功"假象，未来 schema 漂移无法察觉
- **修复**：删除该 UPDATE；改为 `SELECT COUNT(*) ... WHERE is_virtual IS NULL` assert 必须 = 0；任何非零结果都阻断后续 migration

### CRIT-2 · DB-2 — 现有 unique key 与新 unique key 语义冲突，real participant 去重未设计
- **位置**：§1.2 "UNIQUE KEY uk_contest_user_virtual(contest_id, user_id, is_virtual)"
- **证据**：line 164 已有 `UNIQUE KEY (contest_id, user_id, virtual_session_id)`，InnoDB 允许多 NULL，所以同一 `(contest_id, user_id)` 可有多条 real participant；新 unique key 收紧后 ADD UNIQUE 会失败
- **结论**：migration 执行必失败；plan 步骤 §1.2 408-410 行只覆盖虚拟行 dedup，未覆盖真实行
- **修复**：在 `uk_contest_user_virtual` ADD UNIQUE 前先做 real-participant dedup — 保留最早 `registered_at` 一条，其余 `status=DISQUALIFIED` + `finished_at=now`（不要 DELETE，外键引用）

### CRIT-3 · DB-3 — HMAC-SHA256 (64 字符) 写进 `varchar(40)` 列，MySQL 9.1 严格模式直接 1406 错误
- **位置**：§1.3 "HMAC-SHA256(appSecret, contestId + ':' + userId)"
- **证据**：HMAC-SHA256 hex 恒为 64 字符；`virtual_session_id varchar(40)` (line 157) 与 `contest_submissions.virtual_session_id varchar(40)` (line 261)
- **结论**：`startVirtualContest` 在生产环境全面崩溃（直接 DoS 整个虚拟赛功能）；非严格模式才有 2^-96 概率碰撞（finding 数学有误，但走不到这条分支）
- **修复**：同一 migration 加 `ALTER TABLE contest_participants MODIFY virtual_session_id varchar(64) DEFAULT NULL;` + `ALTER TABLE contest_submissions MODIFY virtual_session_id varchar(64) DEFAULT NULL;`；先端到端验证 64 字符写入再写应用代码

### CRIT-4 · DB-4 — Slug dedupe 静默破坏线上公共 URL，缺 301 重定向 + 通知
- **位置**：§1.1 "其余 slug 改为 slug-duplicate-{id后缀} 或软删除"
- **证据**：`contests.slug varchar(120)` 是公开 URL key；`contests.is_deleted` 列已存在但 plan 未使用；无 `redirect_from` 字段、无 history 表
- **结论**：RUNNING 比赛被改名后用户书签/社媒卡/题目集链接全 404，缺运营通知和 redirect 兜底
- **修复**：(1) 加 `slug_redirect_from varchar(120)` + `contest_slug_history` 表；(2) dup 改 `slug-<8字符short-hash>` (36^8 = 2.8T 空间，碰撞可忽略)；(3) 应用层 301 fallback；(4) 迁移前批量邮件 admin + 90 天 301 兼容期

### CRIT-5 · F-ARCH-01 — `findByContestIdAndUserId` 改造范围漏 4 处裸调用点
- **位置**：§1.4 / §5.1 / §9.1
- **证据**：`ContestServiceImpl.java:252` (submitContestProblem 强相关)、`:438` (toVO)、`:478` (toListVO) + `SubmissionServiceImpl.java:1360` 都仍用裸 `findByContestIdAndUserId`，plan §1.4 只列 `ContestSchedulerServiceImpl` 5 处
- **结论**：Phase 2 §2.1 写 "participant.is_virtual == false" 守卫，但 line 254 只校验 `status==STARTED`，虚拟 STARTED session 仍会通过；虚拟 AC 写入真实榜的核心 bug 不闭合
- **修复**：(1) Phase 0 验收加"全仓 11 处调用点清单"硬性 gate；(2) 改造范围扩到 4 个 service；(3) 给旧 mapper 加 `@Deprecated` + ArchUnit 规则禁止业务调用

### CRIT-6 · F-ARCH-07 — Migration 顺序在并发 dev 用户下不安全，缺 dual-write 过渡期
- **位置**：§1.1-1.2 + §9.2 + §10
- **证据**：plan 把 schema constraint 与 app code 改造同 commit；schema 一加就锁表；line 151 NOT NULL DEFAULT 0 (DB-1) 反驳了"NULL 撞唯一键"假设，但 lock_wait_timeout / SELECT FOR UPDATE 仍未指定
- **结论**：prod 部署期 in-flight 写入撞 unique → 500；read-replica 漂移导致用户看到重复 participant
- **修复**：(1) 拆 3 段 migration（add 标识列 + 应用层 dedup runner + ALTER ADD UNIQUE）；(2) 用 `SET SESSION lock_wait_timeout=5` 防长锁等待；(3) 大表考虑 `pt-online-schema-change` / `gh-ost`；(4) `EXPLAIN` + `SHOW WARNINGS` 写入 migration 验证脚本

### CRIT-7 · OPS-01 — 零 feature flag 闸门，5 周全量铺开无独立回滚
- **位置**：§10 排期 + 整体 Phase 0-8
- **证据**：plan 1601 行无 "FeatureFlag/flag/kill.switch" 字样；项目已有 `FeatureFlagsProperties` (含 `useNewContestSystem` 等 6 个 flag) 但 plan 完全不引用；CLAUDE.md 明示 "Feature Flags 通过 FeatureFlagsProperties 管理"
- **结论**：Phase 1-6 任一失败都需 revert commit + rebuild jar + pm2 delete && start；22 commit 链式部署实际无法回滚
- **修复**：(1) 在 `FeatureFlagsProperties` 加 4 个 flag：`contest.virtual-session-isolation.enabled` / `contest.auto-finish.enabled` / `contest.scoring-v2.enabled` / `contest.ranking-isolation.enabled`；(2) 每 Phase 入口用 `@ConditionalOnProperty` 包裹；(3) 准备 Nacos 热刷 + pm2 delete&&start 回滚剧本；(4) Phase 4 评分改动用 shadow-write (rank_new vs rank_for_audit)

### CRIT-8 · FE-02 — BroadcastChannel('virtual-contest') 命名空间 + payload schema 缺陷
- **位置**：§7.2
- **证据**：plan line 990-1016 写 `BroadcastChannel('virtual-contest')` 硬编码全局名；事件只有 name 无 payload schema；无 BroadcastChannel 可用性检测；fallback 一笔带过
- **结论**：未来同 origin 引入"虚拟训练/作业"等会撞名；Tab B 收到非本 contest 事件误清 sessionStorage；Safari 隐私窗口/旧版/iOS WebView 静默失败
- **修复**：(1) 改名 `ulticode-virtual-contest-{contestId}`；(2) payload 强制 `{contestId, virtualSessionId, sourceClientId, timestamp, reason}`；(3) 显式检测 BroadcastChannel 可用性 → storage event fallback + 提示"多 tab 同步不可用" + disable 二 tab 启赛 CTA；(4) sourceClientId 避免自发自收

## 6. 模式分析 (跨 Finding 主题)

### 6.1 共同根因 #1：plan 是"设计文档"而非"实施计划"
- 几乎所有 HIGH/CRITICAL finding 的根源是 plan 只描述 "what"（做什么）不描述 "how"（怎么做）：
  - 缺回滚路径（DB-10, OPS-06）
  - 缺并发原语（RACE-01~08）
  - 缺 schema 兼容性分析（DB-2, DB-3, DB-4）
  - 缺 feature flag / kill switch（OPS-01）
  - 缺可观测性（OPS-04）
- **修复模板**：每个 Phase 增加 "Implementation Constraints" 子节，硬性规定锁策略、事务边界、回滚剧本、监控指标、flag 依赖

### 6.2 共同根因 #2：与 live schema 现状脱节
- 8 个 DB-* finding 中 6 个源于 plan 没核对实际 schema：
  - DB-1：不知道 `is_virtual NOT NULL DEFAULT 0`
  - DB-2：不知道现有 unique key 允许多 NULL
  - DB-3：不知道 `varchar(40)` 不够 HMAC
  - DB-4：不知道 varchar(120) 长度边界
  - DB-13：不知道 `contest_rankings` 已有 `(contest_id, user_id, is_virtual)` unique
- **修复模板**：Phase 0 加 "Schema Reconcile" 子阶段，强制 dump `flyway_schema_history` + 关键表 DDL + 跑一次 EXPLAIN 实际数据后再设计

### 6.3 共同根因 #3：22 commit 中间态在生产不可逆
- F-ARCH-08（5/6 步中间态）、OPS-02（22 commit 链式不可独立回滚）、OPS-03（virtualSessionId 改造致 in-flight 失联）都暴露同一问题
- **修复模板**：commit 分组为 atomic release，每个 release 含 (migration + mapper + controller + feature flag)；release 间 24h 观察期 + dashboard 100% 干净

### 6.4 共同根因 #4：零可观测性
- OPS-04 + RACE-04 + 多个 cache evict 无 traceId → 故障定位靠用户投诉
- **修复模板**：所有 cache evict / listener 触发 / scheduler tick 必须带 traceId + Micrometer 指标 + Nacos 阈值告警

### 6.5 共同根因 #5：scoring / rating 是金融级操作，缺 shadow-mode
- OPS-06 + RACE-05 + DB-12 + DB-7 + F-ARCH-03 都涉及 ranking/Elo 不可逆
- **修复模板**：所有 ranking/Elo 写入必经 (1) `contest_rankings_audit` 双写 (2) 24h 一致率 ≥ 99.99% 才切主 (3) `user_ratings_backup` 24h 可回滚 (4) `contest_rating_freeze` flag

### 6.6 共同根因 #6：CSRF/安全/合规考虑零散
- F-ARCH-10 (CSRF + virtual sessionId), F-ARCH-11 (多租户), PM-11 (虚拟榜隐私), PM-12 (GDPR retention), DB-11 (时区) 各自提到但无统一 security review
- **修复模板**：触发 `security-review` skill 跑一次整体评估

### 6.7 共同根因 #7：产品定位"虚拟赛"被当 P0 之外的"装饰"
