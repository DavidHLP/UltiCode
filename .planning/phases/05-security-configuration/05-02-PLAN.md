  <name>Task 1: Verify XssFilter is a pure pass-through and CSRF headers pass through unmodified</name>
  <files></files>
  <read_first>
    - backend-spring/src/main/java/com/ulticode/common/filter/XssFilter.java (verify pass-through)
    - backend-spring/src/main/java/com/ulticode/security/csrf/CsrfValidationFilter.java (verify it reads headers correctly)
    - backend-spring/src/main/java/com/ulticode/common/config/SecurityConfig.java (verify filter chain order)
  </read_first>
  <action>
    **Verification checklist:**

    1. Read `XssFilter.java` and confirm:
       - The `doFilter` method body is ONLY `chain.doFilter(request, response);`
       - There is NO `HttpServletRequestWrapper` or `HttpServletResponseWrapper` usage
       - There is NO `request.getHeader()` or `response.setHeader()` call
       - There is NO `new XxxRequestWrapper(request)` instantiation

    2. Read `CsrfValidationFilter.java` and confirm:
       - It reads `X-CSRF-Token` header from the original request (not a wrapped one)
       - The header name is exactly `X-CSRF-Token`

    3. Read `SecurityConfig.java` and confirm:
       - `XssFilter` runs at `@Order(Ordered.HIGHEST_PRECEDENCE + 1)`
       - `CsrfValidationFilter` is added AFTER `JwtAuthenticationFilter`
       - The filter chain order is: XssFilter -> JwtAuthenticationFilter -> CsrfValidationFilter
       - No filter between XssFilter and CsrfValidationFilter wraps the request in a way that strips headers

    If ALL of the above checks pass, XssFilter does NOT modify request headers and SEC-08 is satisfied. No code changes needed.

    If any check FAILS (e.g., XssFilter wraps the request), file a finding and describe the exact code that needs to change. But per research, this should be a clean verification.
  </action>
