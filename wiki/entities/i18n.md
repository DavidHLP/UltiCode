# I18n

Per-locale translation storage for UGC-rich entities (problem title/description,
contest intro, solution body, forum post). The DB row is the source of truth
for translated fields; the original entity keeps the canonical (default locale)
content and translations layer on top via `(entityType, entityId, fieldName, locale)`.

## Responsibility

Translate field values for a closed set of translatable entities
(`PROBLEM`, `PROBLEM_DETAIL`, `CONTEST`, `SOLUTION`, `POST`). Read by locale;
admin-only bulk upsert.

## Key tables

| Table | Purpose |
|-------|---------|
| `translations` | one row per (entity, field, locale); `entityType` + `entityId` + `fieldName` + `locale` is the natural unique key |

`Translation` entity maps the row; `entityType` / `entityId` / `fieldName` /
`locale` / `content` are the load-bearing columns.

## Controllers

- `I18nController` → `/i18n`:
  - `GET /i18n/translations?entityType=...&entityId=...&locale=...` — public read.
  - `POST /i18n/translations/bulk` — admin-only; `@RateLimit(30/60s)`; returns
    `{created, updated, skipped}` counts.
  - `GET /i18n/locales` — returns the supported-locale set from
    `I18nConstants.SUPPORTED_LOCALES`.

## Validation

The Translation catalog is self-protecting: `I18nService` validates every
lookup and write against `I18nConstants`, so the controller is a thin HTTP
adapter and internal callers cannot bypass the checks.
- `entityType` must be one of the `TranslatableEntity` values.
- `locale` must be in `SUPPORTED_LOCALES`.
- `fieldName` must be allowed for the entity (e.g. `title`, `summary`,
  `description`, `hints`, `solution`, `content`).

All three violations throw `BusinessException(I18N_INVALID_*)`, which the
global exception handler maps to HTTP 400 with the matching code. For
`bulkUpsert`, every item is validated up front so a partial batch never
persists.

## Flow

admin `POST /i18n/translations/bulk` → `I18nService.bulkUpsert` (per-item
validation → `TranslationMapper` upsert with the `skipDuplicates` flag) →
counts. Public read flows through `getTranslations(type, id, locale)`.

## Gotchas

- Adding a new translatable field is a **three-place** change: entity code, the
  `I18nConstants` field-allow-list, and the front-end fallback. Forgetting any
  one of the three silently drops the value.
- `createdBy` / `updatedBy` come from `SecurityUtil.getCurrentUserId()` — never accept a
  translator identity from the DTO body.
- The public read endpoint returns `Map<String, String>` not a typed DTO;
  callers (front-end) must treat missing fields as `""` / `undefined`, not
  throw.
