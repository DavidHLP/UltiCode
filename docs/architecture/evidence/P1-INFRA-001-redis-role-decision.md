# P1-INFRA-001 Redis Workload Roles and Isolation Decision

> status: ACCEPTED (repository decision; physical split remains conditional)
> evidence: Repository Implemented + Disposable Validatable
> input: `docs/architecture/evidence/P0-BASELINE-004-infra-graph.md`
> scope: current source, executable configuration, ACL materialization, and disposable drills

## Decision

Keep one Redis 7 instance and introduce no new broker. Establish role-named client/config seams for `streams`, `cache`, `rate-limit`, `replay`, `queue`, `judge`, and `pubsub`; initially route every seam to the current Redis endpoint, database, and owner ACL principal. P1-INFRA-002 owns the seam implementation and explicit per-role budgets.

ACL identity/keyspace isolation is not resource or failure isolation. The current ACL gives service users different passwords, commands, key patterns, and (for Pub/Sub) channel patterns. All users still share one Redis process, memory limit, eviction policy, CPU, `maxclients`, persistence/restart boundary, network path, and failure domain. A second instance is justified only by the quantitative disposable-drill triggers in §6.

The decision does not add Kafka, another message broker, a service mesh, Kubernetes, Seata, or an App process split. The legacy RQueue path remains compatibility-only; the normal Judge transport is Redis Streams.

## Evidence boundary

This repository has no production traffic plane. This document makes no production claim about capacity, RPO, RTO, latency, availability, or failover. The numbers below are source/config values or proposed acceptance thresholds for short-lived, isolated, disposable drills. A green disposable drill is not production evidence.

`docker-compose.yml` declares one Redis service with the `redis_data` volume and does not set `maxmemory`, `maxmemory-policy`, AOF, or a Redis-specific RPO/RTO. `docker-compose.ha.yml` is an operator-owned reference profile: it adds a replica, Sentinel processes, and AOF on the primary, but it explicitly does not provide transparent application failover. No production multi-host or Sentinel-aware client claim is made here.

## ACL versus resource/failure isolation

| Boundary | What the current ACL/config does | What it does not do |
|---|---|---|
| Identity | `default` user is off; per-owner users have separate runtime password hashes; health is ping-only; ops/replication/Sentinel users are separate control principals. | It does not give a user a separate Redis process, CPU, memory, `maxclients`, persistence policy, restart, or network failure domain. |
| Keyspace | `resetkeys` plus owner patterns cover the intended namespaces; `stream:integration` is intentionally shared by event producers/consumer groups; Pub/Sub uses `resetchannels` plus an explicit channel pattern. | A key pattern cannot prevent global eviction, memory pressure, command queueing, connection exhaustion, or an instance outage. |
| Commands | `COMMON_COMMANDS` includes the Spring Data, Redisson, Streams, Lua, and inspection commands needed by current adapters; destructive administrative commands remain denied to owner users. | Command allowlists cannot make `allkeys-*` safe for control keys, and cannot establish an RPO/RTO or failover guarantee. |

Current alignment findings are deliberately recorded rather than silently repaired in this source/config-free task:

1. Admin-Audit is a live `stream:integration` consumer, but `ulticode-admin` lacks `~stream:integration`.
2. Notification and Email have live `@RateLimit` endpoints, but `ulticode-notification` lacks `~rate-limit:*`.
3. App's source-referenced token blacklist lookup uses `blacklist:token:*`, but `ulticode-app` lacks `~blacklist:*`; the accepted current policy has no blacklist writer, and the lookup fails closed.
4. `csrf:*`, direct `auth:*`, `poison:*`, `queue:jobs:*`, and `judge:lease:*` are ACL/source reservations with no current Redis writer. Spring cache names are not a missing `cache:*` namespace: actual keys are `<cacheName>::<entry>` and are covered by explicit owner patterns.

These are ACL/keyspace contract findings for P1-INFRA-002. They are not evidence that a second Redis instance or a new broker is needed.

## Role-named seam

P1-INFRA-002 should expose the following logical roles without changing ownership:

- `streams`: `stream:integration`, Search DLQ, and stream inspection/PEL operations.
- `cache`: App/Admin Spring caches only; cache eviction policy may be disposable.
- `rate-limit`: atomic request counters; no silent fail-open fallback.
- `replay`: OAuth state, delegation one-shot markers, and App revocation lookup.
- `queue`: legacy RQueue/status compatibility only; no new normal producer.
- `judge`: fenced Judge Streams, dedup, DLQ, migration lock, and worker connection budget.
- `pubsub`: WebSocket channel publisher/subscriber connections.

The seam keeps service ACL identity separate from role routing: a role client must never let a caller select another owner's ACL or arbitrary key/channel. The initial endpoint map is intentionally boring: every role points to the same `REDIS_HOST`, `REDIS_PORT`, and `REDIS_DB`; role names only make budgets, metrics, key policy, and a future route change explicit. `streams`, `judge`, replay controls, and Search version state require no-eviction treatment; only derived cache entries may be evicted by policy.

## Quantitative disposable-drill triggers for a physical split

These are proposed gates for `P1-INFRA-003`, not production SLOs. Run a representative workload in an isolated Redis with the same ACLs and payload sizes. Capture command p50/p95/p99 by role, `INFO memory`/`INFO stats`/`INFO clients`, PEL/DLQ counts, marker existence, and Worker SLO gauges. Require two independent runs for a non-catastrophic trigger and preserve raw evidence.

| Trigger | Split when observed | Action |
|---|---|---|
| `T-EVICT` (hard) | Any expected control key is evicted or missing under cache flood: `stream:integration`, a Judge/Search stream or DLQ, a non-expired replay marker, Search version hash, or active lock. One key (`> 0`) is sufficient. Also split if `evicted_keys` increases and key-level evidence cannot prove all evictions were cache-only. | Split cache/rate-limit from Streams/Judge/replay/control first; set no-eviction for the control side. Do not “pass” by ignoring the key. |
| `T-LATENCY` | During cache/Pub/Sub load, control commands (`XADD`, `XREADGROUP`, `XACK`, `XPENDING`, Judge SETNX, replay SETNX) show p95 `>50ms` or p99 `>100ms` for 3 consecutive 5-minute windows **and** are `>2×` the quiet baseline in each of two runs. | Separate the noisy cache/Pub/Sub role from control; preserve the role seam and re-run the paired drill. |
| `T-CONNECTION` | `connected_clients / maxclients >= 0.80` for 3 consecutive 5-minute windows, or role connection-borrow timeout/error rate is `>=1%` with p95 borrow wait `>50ms` for 3 windows in two runs, and the control error disappears when the noisy role is isolated. | Split the offending role; make Lettuce/Redisson pool and subscriber budgets explicit before adding capacity. |
| `T-RECOVERY` | After a restart or induced cache-pressure event, any expected stream/PEL/DLQ/replay marker is not restored, or Search/Notification PEL oldest age exceeds `600s` or Judge exceeds `1800s` in two drills, or consume failures stay `>20/5m` for two windows after Redis is healthy. | Split only after ruling out ACL/code/downstream faults; preserve outbox/inbox/replay evidence and require a recovery owner. |
| `T-RESOURCE` | Redis CPU or memory stays `>80%` for 3 consecutive 5-minute windows under the representative workload **and** one of `T-LATENCY`, `T-CONNECTION`, or `T-RECOVERY` also fires in two runs. Raw utilization alone is not a split justification. | Separate the measured noisy role; do not create a new broker from utilization alone. |
| `T-RETENTION` | A newly approved requirement needs a retention/replay horizon or immutable audit log that exceeds the verified Redis Streams envelope, or the required control durability policy cannot coexist with cache eviction. | First evaluate a dedicated Streams/Judge Redis role. Re-open the no-new-broker decision only with measured throughput/retention/replay evidence and a migration/rollback plan. |

A physical split is not triggered by key count, source file count, ACL-user count, or an unmeasured “enterprise” preference. If no trigger fires, keep one instance. If a trigger fires, the smallest next step is a cache/control or Pub/Sub/control split; a new broker remains a separate ADR decision.
