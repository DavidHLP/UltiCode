## 1. Reading rules and method

**Logical locality** means an entity/mapper/service/transaction or contract is owned by the App domain in source and/or by the App schema migration. **Physical deployability** means a separately bootable, independently configured process with its own runtime boundary. The current Maven modules demonstrate the first, not the second: `services/app/pom.xml` is a parent POM whose children are `backend-problem-domain`, `backend-contest-domain`, `backend-submission-domain`, `backend-moderation-domain`, and `backend-app-web` (`services/app/pom.xml:18-30`). The boot artifact is `backend-app-web`; its POM owns the Spring Boot plugin and final executable (`services/app/app-web/pom.xml:247-255`).

`app-web` compiles the four private modules, App/common/API contracts, Submission/Notification/Auth contracts, Redis/MyBatis/MySQL, Dubbo/Nacos, WebSocket, and the optional MeiliSearch client. `backend-judge` and `backend-search` are test-scope dependencies in this POM, not App production dependencies (`services/app/app-web/pom.xml:17-85,209-244`). The private module POMs are library-shaped: Problem, Contest, and Moderation depend on common/app-api plus persistence annotations/validation; the Submission private module contains the App-side entity and persistence annotations but not the owner service (`services/app/modules/problem/pom.xml:12-56`; `services/app/modules/contest/pom.xml:12-55`; `services/app/modules/moderation/pom.xml:12-41`; `services/app/modules/submission/pom.xml:12-56`).

`BackendAppApplication` scans the App shell and all `com.ulticode.modules` packages (`services/app/app-web/src/main/java/com/ulticode/BackendAppApplication.java:15-28`). Production mapper scanning is centralized in `MapperScanConfig` and covers Problem, Contest, Forum, Solution, Moderation, event, and other App-owned mapper packages (`services/app/app-web/src/main/java/com/ulticode/app/config/MapperScanConfig.java:20-45`). The extracted Problem and Moderation domain services are Spring-free and are registered by the App shell (`services/app/app-web/src/main/java/com/ulticode/app/config/AppDomainServiceConfig.java:16-48`). This is a compile/runtime composition seam, not an independent deployable for each private module.

## 3. Cross-domain conclusions

1. **App-owned transactions are local to the App datasource.** Problem, Contest, Forum, Solution, and Moderation write paths use App-local mappers and `@Transactional` boundaries. Cross-owner calls made while an App transaction is open are ordinary RPC/read or command calls; Dubbo does not make them one distributed transaction. Submission explicitly moves its DB transaction to `backend-submission`; Search worker writes Meili; WebSocket delivery is inbox/transport work.
2. **Submission is the deliberate physical exception.** App still compiles a rollback entity/mapper and a local projection, but route conditions prevent normal boot from using them. Canonical `submission.*` tables, grants, intake/verdict transactions, and outboxes are owned by `backend-submission`; App Contest receives association events and owns only contest tables.
3. **Problem, Contest, Forum, Solution, and Moderation are logical modules inside one App process.** Problem/Contest/Moderation private Maven modules deepen compile-time ownership; Forum/Solution remain app-web feature modules. None has an independent boot shell, datasource configuration, migration runner, or production runtime in this evidence. A physical split would require explicit contracts, datasource/migration ownership, transaction compensation, and a separately bootable service; this matrix does not claim that work exists.
4. **Search and WebSocket are integration edges, not business-table owners.** Search writes a derived index through an independent worker and consumes complete versioned events. WebSocket consumes durable inbox events and relays to local STOMP sessions, with optional Redis Pub/Sub fan-out. Neither supports a table/LOC-only deployment split claim.
5. **Cache isolation is logical, not physical.** App cache names (`problem`, `contest`, `contestRanking`, `userStats`, `monitoring`) use one Redis CacheManager with a shared 300-second default. Streams, Pub/Sub, blacklist, cache, and coordination share the Redis instance; key prefixes/role seams do not prove independent failure domains.
6. **The matrix does not recommend a split from size.** Method count, file count, or App web LOC is not used as a decision criterion. Co-change is used only to expose real integration surfaces: Search events across Problem/Forum/Solution, Submission↔Contest association, Moderation↔Auth ban propagation, and SubmissionJudged↔WebSocket.

## 4. Bias and limitations

- This is a repository snapshot, not production evidence. No traffic volume, p95 latency, failure-rate, deployment cadence, or operator ownership telemetry was available.
- The history sample is intentionally short and architecture-heavy (2026-08-11–2026-09-02). It over-represents migration/cutover work and under-represents steady-state feature work; excluded mechanical/format commits would otherwise inflate coupling.
- The graph snapshot predates part of the current source. Direct source/POM/SQL reads are authoritative for this file; graph results were used only for orientation. App migration directories are excluded from graph indexing, so SQL claims are direct-read claims.
- Migration files contain both historical shared-schema shapes and current per-owner paths. The duplicate Admin/App moderation DDL and App rollback Submission shape must not be interpreted as proof of two live writers or two deployable services.
- Cache and Redis observations describe configured code paths and key roles. They do not establish physical Redis isolation, eviction behavior, or production failover.
- RPC annotations prove declared contracts and call topology. They do not prove that Nacos registration, remote endpoints, credentials, or production routing are live.
