## Task 1: Fix --read-only Flag Ordering (SAND-01)

### SAND-01: Fix --read-only flag ordering in Docker command builders

**Files:**
- `backend-spring/src/main/java/com/ulticode/modules/submission/service/impl/SandboxServiceImpl.java`

**Current bug (lines 151-152 in `buildDockerCommand()`, lines 187-188 in `buildBatchDockerCommand()`):**
```java
"--read-only",
"--tmpfs", "/tmp:rw,exec,size=64m",
```
The `--read-only` flag is placed BEFORE `--tmpfs`, which causes the tmpfs mount to fail because `--read-only` makes the filesystem read-only before tmpfs can be mounted.

**Fix:** Swap the order so `--tmpfs` comes first, then `--read-only`:

```java
"--tmpfs", "/tmp:rw,exec,size=64m",
"--read-only",
```

**Acceptance criteria:**
- [ ] `buildDockerCommand()` has `--tmpfs /tmp:rw,exec,size=64m` BEFORE `--read-only`
- [ ] `buildBatchDockerCommand()` has `--tmpfs /tmp:rw,exec,size=64m` BEFORE `--read-only`
- [ ] No other Docker flags are reordered

## Task 2: Volume-Mount Seccomp Profile into Container (SAND-02)

### SAND-02: Add seccomp profile volume mount to Docker sandbox command

**Files:**
- `backend-spring/src/main/java/com/ulticode/modules/submission/service/impl/SandboxServiceImpl.java`

**Current bug:** Line 155 references `--security-opt seccomp=<sandboxConfig.seccompProfilePath()>` but the host path `docker/sandbox/seccomp-profile.json` is never volume-mounted into the container. The container cannot access the seccomp profile.

**Fix:** Add `--volume $(pwd)/docker/sandbox:/seccomp-profile:ro` to both `buildDockerCommand()` and `buildBatchDockerCommand()`. The seccomp `--security-opt` path inside the container will be `/seccomp-profile/seccomp-profile.json`.

Updated security-opt path and new volume mount:
```java
"--volume", "$(pwd)/docker/sandbox:/seccomp-profile:ro",
"--security-opt", "seccomp=/seccomp-profile/seccomp-profile.json",
```

Note: `sandboxConfig.seccompProfilePath()` references the container-internal path, which should be updated to `/seccomp-profile/seccomp-profile.json` OR the config field `seccompProfilePath` in `application.yml` should be changed to `docker/sandbox/seccomp-profile.json` — the volume mount makes the host path accessible at the container path. Since the volume mount `$(pwd)/docker/sandbox:/seccomp-profile:ro` maps `docker/sandbox/seccomp-profile.json` to `/seccomp-profile/seccomp-profile.json`, update the security-opt to use the container path directly.

**Acceptance criteria:**
- [ ] Seccomp profile is volume-mounted into container via `--volume $(pwd)/docker/sandbox:/seccomp-profile:ro`
- [ ] `--security-opt seccomp=` points to the container path `/seccomp-profile/seccomp-profile.json`
- [ ] Both `buildDockerCommand()` and `buildBatchDockerCommand()` have the volume mount

## Task 5: Namespace Isolation Integration Test (SAND-05)

### SAND-05: Create integration test validating namespace isolation

**Files:**
- `backend-spring/src/test/java/com/ulticode/modules/submission/service/impl/SandboxNamespaceIsolationTest.java`

**Test class:** `@SpringBootTest` with `@Testcontainers` for MySQL and any required dependencies. Sandbox execution tested via actual Docker command invocation.

**Tests to implement:**

1. **`processNotVisibleFromHost()`** — After executing code in sandbox, verify the sandbox process is not visible from the host's PID namespace:
   - Execute a long-running dummy code in sandbox (e.g., `sleep 10`)
   - From the host, run `docker ps` or `ps aux` and verify no sandbox process appears
   - Alternatively, check via `/proc` on host — no process with the sandbox's PID exists

2. **`networkIsolated()`** — Verify sandbox network namespace is truly isolated:
   - Execute code that attempts outbound network connection (e.g., `curl http://host.docker.internal`)
   - Connection should fail or timeout (sandbox has `--network none`)
   - Verify the connection cannot reach external addresses either

3. **`userNamespaceIsolated()`** — Verify the process runs as user 1000 inside the container and is not root on host:
   - Execute `id` command in sandbox
   - Verify output shows uid=1000, not uid=0 (root)

**Simplified test approach** (avoids full Testcontainers overhead for Docker-in-Docker):
```java
@Test
void networkIsolated_sandboxCannotReachExternalIP() throws Exception {
    // Execute a curl inside the sandbox container
    List<String> cmd = List.of(
        "docker", "run", "--rm", "--network", "none",
        "ulticode-sandbox:latest", "curl", "-s", "--connect-timeout", "2",
        "http://8.8.8.8"
    );
    ProcessBuilder pb = new ProcessBuilder(cmd);
    pb.redirectErrorStream(true);
    Process p = pb.start();
    int exitCode = p.waitFor();
    String output = new String(p.getInputStream().readAllBytes());

    // Network none means connection refused/timeout — exit code != 0
    assertThat(exitCode).isNotZero();
}
```

**Acceptance criteria:**
- [ ] Integration test class exists: `SandboxNamespaceIsolationTest.java`
- [ ] Test validates PID namespace isolation (sandbox process not visible from host)
- [ ] Test validates network namespace isolation (`--network none` blocks outbound connections)
- [ ] Test validates user namespace (process runs as non-root uid=1000 inside container)
- [ ] All tests pass with `docker build -t ulticode-sandbox:latest -f docker/sandbox/Dockerfile docker/sandbox/` image built
