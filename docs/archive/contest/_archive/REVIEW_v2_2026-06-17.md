## 2. CRITICAL Finding (10 条)

### CRIT-1 · DB-1 · `is_virtual IS NULL` UPDATE 是空操作
- **位置**: PLAN.md §1.2
- **证据**: `V20260602_120000__Create_All_Tables.sql:151,223,303` 三处 `is_virtual tinyint(1) NOT NULL DEFAULT '0'`，物理上不可能存 NULL
- **修复**: 删 UPDATE；改 `SELECT COUNT(*) WHERE is_virtual IS NULL` assert = 0
- **来源**: REVIEW.md §2

### CRIT-2 · DB-2 · 新 unique key 与现有 unique key 语义冲突
- **位置**: PLAN.md §1.2
- **证据**: line 164 已有 `UNIQUE KEY (contest_id, user_id, virtual_session_id)`，InnoDB 允许多 NULL
- **修复**: ADD UNIQUE 前先 real-participant dedup（保留最早 `registered_at`，其余 DISQUALIFIED + finished_at）
- **来源**: REVIEW.md §2

### CRIT-3 · DB-3 · HMAC-SHA256 64 字符写进 `varchar(40)` 列 → DoS 整个虚拟赛
- **位置**: PLAN.md §1.3
- **证据**: HMAC-SHA256 hex = 64 字符；`virtual_session_id varchar(40)` (line 157, 261)
- **修复**: 同 migration 加 `ALTER TABLE ... MODIFY virtual_session_id varchar(64) DEFAULT NULL;`
- **来源**: REVIEW.md §2

### CRIT-4 · DB-4 · Slug dedupe 静默破坏线上公共 URL
- **位置**: PLAN.md §1.1
- **证据**: `contests.slug varchar(120)` 公开 URL key；无 `redirect_from` / history 表
- **修复**: 加 `slug_redirect_from` + `contest_slug_history` + 应用层 301 fallback + 运营通知
- **来源**: REVIEW.md §2

### CRIT-5 · F-ARCH-01 · `findByContestIdAndUserId` 改造漏 4 处裸调用
- **位置**: PLAN.md §1.4 / §5.1 / §9.1
- **证据**: `ContestServiceImpl.java:252,438,478` + `SubmissionServiceImpl.java:1360`
- **修复**: Phase 0 加"全仓 11 处调用点清单"硬性 gate；旧 mapper 加 `@Deprecated` + ArchUnit 规则
- **来源**: REVIEW.md §2

### CRIT-6 · F-ARCH-07 · Migration 顺序在并发 dev 用户下不安全
- **位置**: PLAN.md §1.1-1.2
- **证据**: schema constraint 与 app code 改造同 commit，schema 一加就锁
- **修复**: 拆 3 段 migration（add 标识列 + 应用层 dedup runner + ALTER ADD UNIQUE）+ `lock_wait_timeout=5`
- **来源**: REVIEW.md §2

### CRIT-7 · OPS-01 · 零 feature flag，5 周全量铺开无 SRE kill switch
- **位置**: PLAN.md §10 整体
- **证据**: 1601 行无 "FeatureFlag/flag/kill.switch" 字样；项目已有 `FeatureFlagsProperties` 但 plan 不引用
- **修复**: 加 4 个 flag（virtual-session-isolation / auto-finish / scoring-v2 / ranking-isolation）+ `@ConditionalOnProperty`
- **来源**: REVIEW.md §2

### CRIT-8 · FE-02 · BroadcastChannel 全局命名 + payload schema 缺陷
- **位置**: PLAN.md §7.2
- **证据**: `BroadcastChannel('virtual-contest')` 硬编码全局名；事件只有 name 无 payload schema
- **修复**: 改名 `ulticode-virtual-contest-{contestId}` + payload 强制 schema + 可用性检测 + storage event fallback
- **来源**: REVIEW.md §2

### **CRIT-9 · F-SEC-01 · `X-Virtual-Session-Id` 客户端控制导致横向越权** ⭐ v2 新增

- **位置**: PLAN.md §2.2 (line 494-510) + `ContestServiceImpl.submitContestProblem`
- **证据**: `HMAC-SHA256(appSecret, contestId + ':' + userId)` —— **sessionId 是 (userId, contestId) 的纯函数**，无随机 salt，无 userId 绑定 nonce
- **致命点**:
  1. **真正鉴权应当绑定 userId**：plan §1.3 说"真正鉴权仍然来自登录用户 + participant 归属校验"，但 §2.2 的逻辑只说"查 virtual participant"。若 mapper 接受任何 sessionId，A 用 B 的 sessionId（抓取 / 泄漏）就能以 B 身份提交
  2. **跨设备 IDOR**：A 设备开虚拟，B 设备 join，sessionId 一致 = 覆盖 A 进度
  3. **Replay**：sessionId 不变 = 抓包后可重复提交
  4. **WS handler 同 mapper**：WS join 也等价 IDOR
- **修复**:
  1. mapper 强制 `WHERE virtual_session_id=? AND user_id=?`，userId 来自 `@AuthenticationPrincipal`，**绝不**接受 query/header 里的 userId
  2. sessionId 改为 `HMAC(appSecret, userId || contestId || startedAt || randomNonce)`，nonce 存 participant 行
  3. WS join 同样按 (userId, sessionId) 双 key 校验
  4. 加 IT 测试：用户 A 拿 B 的 sessionId 提交 → 403
- **来源**: SECURITY_REVIEW.md F-SEC-01

### **CRIT-10 · F-SEC-02 · `appSecret` 在项目中不存在，HMAC 治理真空** ⭐ v2 新增

- **位置**: PLAN.md §1.3 (line 419-431)
- **证据**: 计划原文 `HMAC-SHA256(appSecret, ...)`；但项目 `application.yml` / `JwtProperties` / `FeatureFlagsProperties` **无任何 `appSecret` 字段**
- **5 个具体风险**:
  1. **空密钥退化**：null → NPE；空字符串 → 任何人都可预测 sessionId
  2. **借 JWT secret 顶替**：复用 jwt.secret → JWT 轮换 = 虚拟赛 session 全部断链，UX 崩
  3. **多环境一致性**：dev/staging/prod 共享？各自随机？未设计
  4. **轮换方案缺失**：轮换 = 老 session 全部失效，无双 secret 灰度
  5. **泄露后果**：appSecret 泄漏 = 永久伪造任意 (userId, contestId) 的合法 sessionId
- **修复**:
  1. 新建 `VirtualContestProperties` 显式 `appSecret` 从 `VC_HMAC_SECRET` env 注入，启动 fail-fast 校验 ≥ 32 字节
  2. **禁止**复用 JWT secret
  3. 双 secret 轮换：新 secret 生效后老 secret 仍可校验 7 天（`valid_from` / `valid_to` 列）
  4. 多环境 secret 来源文档化（CI secret / Nacos / .env）
- **来源**: SECURITY_REVIEW.md F-SEC-02

## 3. HIGH Finding (v2 新增 4 条)

> 完整 31 条 HIGH 见 `REVIEW.md` §3。v2 Security 重试新增 4 条关键 HIGH：

### **HIGH-SEC-1 · F-SEC-03 · `is_virtual` API 可写，无 DB CHECK → 虚拟→真实伪造污染真榜+Elo**
- **关切**:
  1. mapper `@Param("isVirtual")` 注入，admin 后台能改 → 虚拟 AC 变真实 AC → 触发 Elo + 成就
  2. 无 CHECK 约束：dev/seed 误插入 is_virtual=2/-1，三元判断绕过
  3. **反向攻击**：用户 POST `is_virtual=false` 强制真实参赛，绕过"虚拟赛不参与真榜"产品决策 = **产品级越权**
- **修复**: `@Column(updatable=false)` + DB `CHECK (is_virtual IN (0,1))` + `chk_virtual_pair` + BEFORE UPDATE trigger + admin SUPER_ADMIN 专用入口
- **来源**: SECURITY_REVIEW.md F-SEC-03

### **HIGH-SEC-2 · F-SEC-04 · WS join 鉴权 race + 旁观/公开房间泄漏**
- **关切**:
  1. **race**: virtual STARTED → auto-finish 之间 join WS，handler 拒绝但 user 已收到 race 期间 WS 帧
  2. **未鉴权 join 公开房间**："比赛允许公开旁观"没定义 = 旁观者能 subscribe `/topic/contest/{id}/submission-result` 看他人判题结果（含失败堆栈）
  3. **广播大小**：排行榜 N=5000，每 1-2s 推 = 1MB/次，无 diff 推送 = 客户端 OOM
- **修复**: `contest.spectatorEnabled` 显式默认 false + handler 顺序 authn→participant→spectator flag + ranking diff 推送 + announcement `@PreAuthorize`
- **来源**: SECURITY_REVIEW.md F-SEC-04

### **HIGH-SEC-3 · F-SEC-05 · HMAC deterministic sessionId = 预测/共享/持久 IDOR**
- **关切**:
  1. **跨设备 IDOR**：同 userId+contestId 跨设备 sessionId 一致
  2. **跨比赛稳定性**：可离线枚举生成任意 (userId, contestId) 的合法 sessionId
  3. **持久化攻击**：DB 已存在 startedAt > current 的虚拟 participant，攻击者 join 触发 finish 老 session
- **修复**: sessionId 加 `randomNonce` + `startedAt` 盐值每次 start 重生成 + submit 接口 idempotency-key
- **来源**: SECURITY_REVIEW.md F-SEC-05

### **HIGH-SEC-4 · F-SEC-07 · `penaltyPerWrong` / `tieBreaker` admin 改值可被实时作弊**
- **关切**: 比赛进行中 admin 改 ICPC → IOI / penalty 600 → 0 / isRated=true → false → 排名瞬间反转 + 跳 Elo，**无审计无锁定**
- **修复**: RUNNING 状态 scoring 字段 `updateable=false` + FINISHED 改后触发 final_rank 重算 + `@Audited` + isRated 改触发监控告警
- **来源**: SECURITY_REVIEW.md F-SEC-07

## 6. 模式分析 (跨 Finding 主题，含 v2 安全视角)

### 6.1 共同根因 #1：plan 是"设计文档"而非"实施计划"
- **v1 观察**：缺回滚路径、并发原语、schema 兼容性分析、feature flag、可观测性
- **v2 安全补充**：缺安全章节（OWASP / STRIDE）、缺 HMAC/secret 治理、缺 is_virtual API 保护规范

### 6.2 共同根因 #2：与 live schema 现状脱节
- **v1 观察**：8 个 DB finding 中 6 个未核对实际列定义
- **v2 安全补充**：未核对实际 secret 配置（appSecret 不存在）、未核对 WS handler 是否真按 userId 校验

### 6.3 共同根因 #3：22 commit 中间态在生产不可逆
- **v1 观察**：任意 1-2 commit 窗口期会脏
- **v2 安全补充**：appSecret 引入也需 dual-write 过渡，否则 in-flight virtual session 失联

### 6.4 共同根因 #4：零可观测性
- **v1 观察**：无 metric / dashboard / traceId
- **v2 安全补充**：无安全 audit log、无异常登录告警、无 IDOR 尝试告警

### 6.5 共同根因 #5：scoring/rating 缺 shadow-mode
- **v1 观察**：ranking/Elo 不可逆
- **v2 安全补充**：admin 改 scoring 字段无审计 + 无锁定（CRIT-7 + HIGH-SEC-4）

### 6.6 共同根因 #6：CSRF/安全/合规零散
- **v1 观察**：F-ARCH-10/11、PM-11/12、DB-11 各自提到无统一评估
- **v2 强化**：CRIT-9/10 暴露**客户端控制鉴权 + secret 真空**是更基础的安全缺陷

### 6.7 共同根因 #7：产品定位"虚拟赛"被当装饰
- **v1 观察**：Editorial/Clarification/封榜压到 Phase 8
- **v2 安全补充**：反作弊（开卷/刷题/LLM 协助）完全空白（HIGH-SEC PM-10 / F-SEC-12）

### 6.8 共同根因 #8 ⭐ v2 新增：HMAC/session 设计假设未验证
- 计划假定 `appSecret` 存在并可管理，但项目实际无此配置
- 计划假定 sessionId 是 `(userId, contestId)` 纯函数足够安全，但漏掉 deterministic = 可预测
- 计划假定 client header 是路由 hint，但漏掉"client header 也可被攻击者控制"
- **修复模板**：每个新鉴权/标识设计必须先验证 (1) 实际配置存在 (2) 包含不可预测 nonce (3) 服务端 binding 到 principal 而非 header
